# Подключение Supabase, Resend и Render

Это инструкция по настройке подготовленного проекта. Созданный аккаунт сервиса сам по себе не подтверждает, что приложение подключено к нему. Не публикуйте секретные ключи и не отправляйте их в чат.

## 1. Supabase

Откройте проект **SimpleSchedule**. Убедитесь, что в нём нет чужой рабочей схемы с теми же именами таблиц. Выполните `PWA/supabase/schema.sql` в SQL Editor. Скрипт создаёт таблицы приложения, RLS, RPC синхронизации и закрытое хранилище сессий. Сначала проверьте его в dev-проекте.

Для текущего проекта Project URL: `https://kofrjmkffcwkuuljdgez.supabase.co` (без `/rest/v1/`). Из настроек проекта понадобятся:

| Значение | Где используется |
| --- | --- |
| Project URL `https://….supabase.co` | `Supabase__Url` на сервере Render |
| Publishable key | `Supabase__PublishableKey` на сервере |
| Service role/secret server key | `Supabase__ServiceRoleKey`, только сервер; запрещён в клиенте |
| Случайный ключ AES, 32 байта в Base64 | `Session__EncryptionKey`, только сервер |

Создать ключ сессий можно локально командой `openssl rand -base64 32`, затем вставить результат в секретную переменную Render. Это не API-ключ Resend. Сохраните его в менеджере паролей; замена завершит существующие сессии.

В **Authentication → Providers → Email** включите email-вход и создание пользователей. В шаблоне **Magic Link** должен быть код `{{ .Token }}`, а не только ссылка. Выберите шестизначный код, срок действия 10 минут и разумный интервал повторной отправки (например, 60 секунд); названия полей панели могут меняться. Настройки проверить реальным входом до открытия доступа пользователям.

Русский шаблон письма:

```html
<h2>Вход в SimpleSchedule</h2>
<p>Ваш одноразовый код:</p>
<p style="font-size:32px;letter-spacing:8px;font-weight:bold">{{ .Token }}</p>
<p>Введите код в приложении. Если вы не запрашивали вход, просто проигнорируйте письмо.</p>
```

Настройте Site URL на HTTPS-адрес Render. Удалите ненужные redirect URLs. Код API не получает доступ к почтовому ящику пользователя.

## 2. Resend и домен

Адрес `noreply@simple-schedule` не подходит для выбранной публичной почтовой доставки. Нужен реальный домен, которым вы управляете, например `noreply@simple-schedule.ru` **только если он ваш**. Адрес в примере не является зарегистрированным адресом проекта.

1. Добавьте домен/почтовый поддомен в Resend → Domains. Для уже имеющегося `pouqwyggad123.shop` рекомендуется отдельный `notify.pouqwyggad123.shop` с отправителем `SimpleSchedule <noreply@notify.pouqwyggad123.shop>`; окончательный адрес зависит от подтверждённого в Resend домена.
2. В действующей DNS-зоне Cloudflare добавьте **только записи, которые выдал Resend** для этого поддомена. Дождитесь статуса Verified. Если NS уже указывают на Cloudflare, записи добавляются там, а не в неактивной DNS-зоне регистратора Regway. Существующие записи VPS и nameservers не меняйте. Почтовые DNS-записи публикуются без HTTP-proxy Cloudflare.
3. Создайте ключ только для отправки писем, с нужным ограничением домена, если доступно.
4. В Supabase → Authentication → SMTP укажите подтверждённый sender, имя SimpleSchedule, SMTP host `smtp.resend.com`, username `resend`, password — API-ключ. Выберите порт и TLS по текущей инструкции Resend (например, 465 с TLS).
5. Отключите отслеживание открытий/переходов в письмах авторизации.

Отдельный купленный почтовый ящик `noreply` обычно не требуется для SMTP-отправки; DNS и подтверждение домена обязательны. Встроенная тестовая почта Supabase имеет ограничения по адресам и частоте, её нельзя представлять как готовую production-доставку.

Источники: [Supabase email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [Resend SMTP](https://resend.com/docs/send-with-smtp).

## 3. Render

В Render создайте Web Service из `pouqwyggad1/SimpleSchedule`, ветка **pwa-ios**. Можно использовать Blueprint **PWA/render.yaml** либо задать:

- Runtime: Docker.
- Root Directory: `PWA`.
- Dockerfile: `./Dockerfile`; Docker build context — корень выбранного каталога PWA.
- Health check: `/health`.
- Сервис слушает `0.0.0.0:8080`.
- Переменные Supabase и шифрования из таблицы выше; ничего из этого не добавлять в `VITE_*`.
- `PublicOrigin` — полный HTTPS-origin сервиса без конечного `/`, для проверки запросов на изменение данных.

Сначала можно использовать `onrender.com`; свой домен для самого сайта необязателен. Адрес сайта и домен отправителя писем — разные настройки.

Проверьте `/health`, открытие календаря, настройки и реальный цикл «код → вход → создать дело → войти на втором устройстве → получить дело». Затем проверьте выход и изоляцию другого аккаунта. Наличие зелёного статуса сборки не подтверждает доставку письма или RLS рабочего проекта.

План `free` указан для разработки. Он засыпает при простое; почасовой импорт и будущие своевременные push требуют работающего сервера либо надёжного внешнего планировщика. Не включайте платные ресурсы без выбранного вами тарифа.

## 4. Завершить подключение

После живой проверки добавьте реальный HTTPS-адрес в раздел установки README. Проверьте на iPhone: добавление на главный экран, повторное открытие, локальные правки без сети, восстановление связи, вход и синхронизацию. При обновлении приложения сохраняйте тот же origin, иначе браузер создаст отдельное локальное хранилище.

Уведомления Web Push — будущий этап: отдельный серверный отправитель, VAPID, подписки каждого устройства и очередь напоминаний. Подготовленные переключатели не являются подтверждением доставки. Apple Developer Program для стандартного Web Push PWA не требуется.
