# Настройка сервера SimpleSchedule PWA

Исходники готовы к сборке без доступа к вашему аккаунту. Реальные вход по почте, облачный обмен и автоматический импорт начинают работать после настройки проекта и окружения; локальные данные/календарь не зависят от Supabase.

## Supabase

1. В проекте откройте SQL Editor и выполните `PWA/supabase/schema.sql`. Это bootstrap-схема с RLS и RPC. Не запускайте `server.tests/mock-auth.sql` в Supabase: она нужна только для изолированных локальных тестов.
2. В Authentication включите Email. В шаблонах Magic Link и подтверждения регистрации используйте русский текст и `{{ .Token }}`, а не только ссылку. Например:

   ```html
   <h2>Вход в SimpleSchedule</h2>
   <p>Ваш одноразовый код: <strong>{{ .Token }}</strong></p>
   <p>Если вы не запрашивали вход, просто проигнорируйте письмо.</p>
   ```

3. Настройте шестизначный OTP, срок действия 600 секунд и ограничение повторной отправки. Дополнительно API ограничивает число запросов/попыток с одного IP. Эти ограничения не заменяют настройки Auth.
4. В Custom SMTP задайте настройки Resend: `smtp.resend.com`, порт `465`, пользователь `resend`, пароль — API-ключ Resend. Адрес отправителя должен принадлежать подтверждённому в Resend домену, например `noreply@ваш-домен.ru`; `noreply@simple-schedule` без реального домена не подходит. Отключите tracking для писем входа.
5. В Site URL задайте HTTPS-адрес Render/PWA. Настройте пределы отправки писем согласно вашей нагрузке. API-ключ Resend хранится в Supabase SMTP, собственная генерация кодов приложением не нужна.
6. В Project Settings возьмите Project URL, publishable key и secret/service-role key. Привилегированный ключ храните **только в серверных переменных Render**, не в frontend и не в Git.

Схема закрывает таблицу шифрованных серверных сессий от `anon`/`authenticated`; чтение/правка пользовательских записей использует `auth.uid()`, RLS и проверенные RPC. Включённый PostgreSQL Data API должен показывать функции `pwa_sync` и серверные RPC. Схема задаёт явные GRANT и посылает reload schema; если в проекте отключена экспозиция public schema, настройте её в Data API.

## Переменные сервера

| Переменная | Значение |
| --- | --- |
| `ASPNETCORE_URLS` | `http://+:8080` в контейнере |
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `PublicOrigin` | Точный HTTPS origin, например `https://simple-schedule.onrender.com`, без завершающего `/` |
| `Supabase__Url` | `https://<project-ref>.supabase.co` |
| `Supabase__PublishableKey` | Publishable key проекта |
| `Supabase__ServiceRoleKey` | Secret/service-role key, только backend |
| `Session__EncryptionKey` | Base64-представление 32 случайных байтов; постоянное между перезапусками |
| `ScheduleWorker__Enabled` | `true` для серверного автообновления |
| `Jobs__Secret` | Случайная строка длиной не менее 32 символов для внешнего планировщика |

Секрет шифрования можно локально сгенерировать `openssl rand -base64 32`. Сохраните его в Render secret environment; не публикуйте результат в чат или репозиторий. Смена ключа делает старые серверные сессии нечитаемыми, потребуется повторный вход.

Cookie `ss_session` содержит случайный непрозрачный ID: `HttpOnly`, `Secure` в production, `SameSite=Strict`, путь `/api`, срок 30 дней. Access/refresh tokens хранятся шифрованными AES-256-GCM в Supabase и обновляются под краткой серверной lease. Код и токены не возвращаются JavaScript. POST-запросы требуют JSON и точный разрешённый Origin.

При локальной разработке frontend на `http://127.0.0.1:5173`, backend на `http://127.0.0.1:5080` и proxy `/api` задайте `PublicOrigin=http://127.0.0.1:5173`, `ASPNETCORE_ENVIRONMENT=Development`. Имя хоста должно совпадать: `localhost` и `127.0.0.1` — разные origins. Не включайте Development в Render.

## Автоматическое обновление

Настройка аккаунта «Автоматически» создаёт постоянное задание в Supabase с интервалом 1/3/6 часов. Сервер обновляет текущий и следующий месяц по часовому поясу `Asia/Irkutsk`, объединяет исходные занятия с личными правками и публикует одну транзакцию. В режиме «Вручную» задания нет.

Встроенный worker проверяет очередь раз в минуту, пока сервис работает. Для Render free, который может засыпать, или для независимого запуска настройте защищённый Cron-запрос:

```text
POST https://<ваш-адрес>/api/jobs/run
Authorization: Bearer <Jobs__Secret>
```

Этот endpoint обрабатывает одно наступившее задание и использует ту же постоянную lease, что встроенный worker. В Supabase Cron можно вызывать его через `pg_net`; URL и Bearer secret держать в Vault, а не в публичном SQL-файле. Пример и частоту настраивайте под выбранный тариф. При нескольких аккаунтах вызывайте чаще или используйте постоянно работающий сервер. Точность интервалов зависит от доступности сервера/планировщика, не от фоновых таймеров Safari.

Сбой недели/неопубликованный хвост не очищает данные. Если не получено ни одного подтверждённого дня, worker оставляет текущую версию и повторяет через 15 минут. Личные заметки, ДЗ и ручные поля сохраняются. Отменённая пара с личными правками превращается в ручную запись. Пара без личных правок скрывается флагом `sourceCancelled` и автоматически возвращается с тем же ID, если сайт восстановит её. Tombstone создаётся только при явном удалении пользователем и не отменяется импортом. Push-уведомления пока не отправляются: настройки сохранены для будущего этапа.

## Проверка

- `GET /health` — процесс доступен.
- `GET /api/health` — в том числе факты конфигурации Auth/worker; наличие конфигурации само по себе не доказывает доставку писем.
- Открыть PWA, получить код на свою почту, войти; на втором устройстве повторить вход тем же адресом и проверить обмен данными.
- Проверить отказ в доступе другому пользователю, отзыв cookie, офлайн очередь и повтор после перезапуска Render.
- Для локального C#-набора: `dotnet run --project PWA/server.tests/SimpleSchedule.Pwa.Tests.csproj`.
- Для отдельного тестового PostgreSQL: сначала `server.tests/mock-auth.sql`, затем `supabase/schema.sql`, затем `server.tests/sync-regression.sql`. Сценарий rollback проверяет RLS, конфликты, идемпотентность, удаление групп, worker/session leases. Реальный Supabase Auth/SMTP этим тестом не заменяется.
- `PSQL=psql PGHOST=127.0.0.1 PGPORT=<порт тестового кластера> PGDATABASE=postgres python3 PWA/server.tests/postgres-concurrency.py` дополнительно проверяет двумя параллельными транзакциями, что снимок ждёт COMMIT и не пропускает поздно подтверждённую ревизию. Запускать только в отдельном тестовом кластере.
- `python3 PWA/server.tests/http-regression.py http://127.0.0.1:5081` проверяет CSRF/Origin, no-store и ответы локального сервера без настроенных Auth-ключей. Для этого сервера задать Development, порт 5081 и `PublicOrigin=http://127.0.0.1:5173`.

Официальные инструкции: [email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [Resend SMTP](https://resend.com/docs/send-with-smtp), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
